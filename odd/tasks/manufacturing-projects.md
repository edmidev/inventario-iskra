## Specs
- S1 Project templates: name, description, text characteristics, exact inventory tools, per-unit consumable quantities and estimated calendar days. User: "Esta entidad proyecto, llevara un nombre, una descripcion, un listado de caracteristicas, y tambien llevara un listado de consumibles del inventario y herramientas que se necesitan para llevar a cabo este proyecto".
- S2 Executions permanently snapshot template; integer unit count scales consumables only, not tools or duration. Duration editable on registration. User: "lo que ya esta registrado queda asi, registrado"; "una ejecucion puede fabricar varias unidades si se quiere"; "cuando se este registrando la ejecucion eeste sea edutable se oyede ajustar".
- S3 One principal responsible user (any active user) and multiple assigned workers. States registered, in progress, paused, completed, cancelled. Partial start allowed with missing materials/tools. User: "varios responsables, uno principal y varios trabajdores asignados"; "cualquier usuarios de momento"; "se puede iniciar parcialmente, porque se puede ir solventando mientras se va ejecutando el proyecto".
- S4 Tools are exact informational assets, shared across executions; no reservation or execution-specific checkout. User: "una herramienta puede ser usada por varias ejecuciones al mismo tiempo, el tema de de las herramientas es para saber que herramientas se necesitan".
- S5 Consumables support up to three decimal places across stock, purchasing, importer and dashboard. Preserve historical visible quantities, asset integrality, and money in minor units. User: "si, debemos permitir decimales"; "si, hasta 3 decimales". Accepted plan default: round each purchase subtotal to nearest cent, half up.
- S6 Reserve available quantities globally by item at execution registration; physical location selected at delivery. Record delivery as stock out, consume own reservation atomically; explicit returns as stock in. User selected "Reservarlos (Recommended)" and accepted item-global reserves, physical delivery tracking and returns.
- S7 Physical count overrides reservations: allocate actual remaining quantities oldest-execution-first, expose deficits; ordinary stock out must not consume other executions' reservations. Free inbound and leftovers fill oldest active needs; earmarked inbound honors destination first. User: "si, hay que reflejar la cantidad real"; "aca te dejo la decision a ti, que se lo mas recomendable".
- S8 One automatic shortage request per execution (not a supplier order); create linked supplier purchases, record what/where/how much and costs. Existing supplier-order lifecycle retained; receive stock and allocate atomically and idempotently. Display unpurchased vs purchased-pending quantities to avoid duplicate procurement. User selected "Una por ejecución"; "debemos registrar compras, que se compro, donde se compro, cuanto de cada articulo se compro"; "si, quedan reservados automaticamente".
- S9 Additional execution consumables are total quantities for that whole execution (not per-unit); they can be added at registration and later while the execution is active, without mutating the project template. Additional tools can also be added at registration and during execution; they remain informational and execution-specific, without reservation or exclusive checkout. Terminal execution releases reservations; delivered unused materials explicitly returned, never implicitly credited. Do not auto-cancel supplier orders; receipts after cancellation become general inventory. User: "si claro"; "acepto tu recomendacion"; "en ambos casos se puede agregar consumibles"; "como total para toda la ejecucion"; "si, si quuiero que se puedan registrar tanto al inicio como durante la ejecucion del proyecto".
- S10 Automatic events plus typed manual positive/negative developments, actor and timestamp; execution timeline and all-execution weekly view with date/customer/status/responsible filters. User: "todo tipo de inicencias, buenas y malas"; "se inicio el proyecto"; "se termino el proyecto"; "falta un material x"; "se compro x material"; "si, me gustaria esa vista general de todas las ejecuciones". Default week Monday-Sunday, America/Caracas.
- S11 Persist dynamic role permissions and admin configuration UI, enforce current effective permissions server-side and use them in frontend guards. Requested roles: "administrador", "jefe taller", "supervisor", "jefe de inventario", "trabajador". User: "pongamos la pantalla para que el administrador pueda asignar permisos a los roles dinamicamente sin mdoificr el codigo". Preserve operator/viewer legacy access until reassignment; seed new roles without invented grants; retain last-admin anti-lockout. One role per user retained.
- S12 Clients required on execution, multiple clients supported now, unit allocation only at delivery. User: "siempre erea obligatorio registrar al cliente"; explicit selection "Varios clientes desde ahora"; "la dejamos al final, cuando ya este el producto decidimos a que cliente va cada producto".
- S13 Partial production and deliveries; each finished unit gets unique generated PRD-000001-style code, traceable to execution and delivery recipient. Separate finished stock from tools/consumables; prevent duplicate delivery. Complete manufacturing only after planned units produced; delivery not required to complete. User: "cada producto debe tener un codigo unico que le vamos a generar". Preserve produced units on cancellation.
- S14 Customer CRUD and printable numbered delivery receipt with date, client and unit codes. User: "si, dale incluyamos esas etapas"; "si, me gustaria". No sales, invoices, payment accounting, automatic unit conversion or remote publication.
- S15 Reuse existing hexagonal modules and db.WithTx/db.Begin transaction seam; centralize reservation enforcement in locked stock recording. Consistent item-lock ordering and idempotent writes; avoid deadlocks and duplicate stock effects. Expand OpenAPI, README and Spanish UI while keeping identifiers/comments English. Existing dirty .atl registry files untouched.
